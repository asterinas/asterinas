# Components

In the current Asterinas component system, a component crate registers one or
more boot-time initialization hooks with the staged initialization framework
through `#[init_component]`.

Component crates are ordinary Cargo crates. Their `Cargo.toml` dependencies
define what code is compiled, linked, and callable. The component framework
adds initialization discovery and ordering; it does not replace Cargo's
dependency model.

## Initialization hooks

A component crate may register at most one initialization function for each
stage:

- `#[init_component]` or `#[init_component(bootstrap)]` registers a
  `Bootstrap` hook. It runs on the bootstrap processor after OSTD
  initialization and before the core subsystem initialization.
- `#[init_component(kthread)]` registers a `Kthread` hook. It runs from the
  first non-idle kernel thread.
- `#[init_component(process)]` registers a `Process` hook. It runs when the
  first user process starts.

Each hook has the following shape:

~~~rust
use component::{ComponentInitError, init_component};

#[init_component(kthread)]
fn init() -> Result<(), ComponentInitError> {
    // Initialize state that requires kernel-thread context.
    Ok(())
}
~~~

The component macros collect these hooks at link time. For each stage,
`aster-core` calls `component::init_all` with metadata generated by
`component::parse_metadata!`.

Within a stage, the framework derives priorities from the Cargo dependency
graph. If component A depends on component B, B's hook runs before A's hook in
that stage. A hook error is reported through the boot log, and initialization
continues with the remaining hooks. Component metadata mismatches abort the
current boot sequence.

## Component layers

Components are classified by their position relative to `aster-core`.

| Kind | Location | Dependency rule | Current state |
|------|----------|-----------------|---------------|
| Low-level | `kernel/core/comps/` | May be named by `aster-core`; must not depend on `aster-core` | Contains all existing component crates |
| High-level | `kernel/comps/` | May depend on `aster-core`; must not be named by the core or lower crates | Reserved; no high-level component is currently implemented |

Reusable kernel crates that do not register component initialization hooks and
do not require `aster-core` APIs normally belong under `kernel/libs/`. Code
should be placed directly in `aster-core` only when moving it to a higher-layer
crate would require `aster-core` or a lower-layer crate to depend on that crate
by name, and a lower-owned interface cannot reasonably invert the dependency.

This classification is defined by dependency direction, not only by directory
placement. A component that depends on core services cannot simultaneously
remain a dependency of `aster-core`, because that would create a Cargo
dependency cycle.

## Cross-layer interfaces

When lower-layer code needs behavior supplied by a high-level component, the
lower layer owns the interface and registration point. The high-level
component implements and registers that interface during initialization.

Asterinas does not provide a universal cross-layer registry. Each subsystem
defines an interface and registration mechanism appropriate to its semantics.

## Inclusion and metadata

Existing low-level components are included through ordinary Cargo dependency
relationships: each is a direct or transitive dependency of `aster-core`. The
component framework does not provide a generic assembler-level component
selection mechanism.

`parse_metadata!` treats every workspace package that directly depends on the
`component` crate as a metadata participant. Each participant must be listed in
the root `Components.toml`. This includes `aster-core`, because it invokes
`parse_metadata!` and `init_all`, even though `aster-core` is not itself a
component crate.

`Components.toml` serves as a validation manifest for metadata participants.
Initialization priorities are computed from dependency relationships reported
by Cargo metadata, rather than from the order or structure of entries in
`Components.toml`. The file does not force a package to be linked.

## Constraints and limitations

Components are statically linked build-time units. Runtime loading, unloading,
and replacement are not provided by the current component framework.

Kernel components are required to remain on the safe-Rust side of the
framekernel boundary. Operations that require unsafe Rust belong in OSTD
behind sound safe APIs.
